**三 一次请求如何变成声音**

```text
业务提交文本和音色标识
        ↓
HTTP 路由校验参数和鉴权
        ↓
读取参考音频及转写文本，编码或复用缓存
        ↓
文本进入 Drama 3，按需要分段生成离散音频编码
        ↓
codec 解码成波形
        ↓
返回 WAV 等音频字节，或按文本段发送音频流
```

模型权重提供通用生成能力；参考音频与对应转写文本用于引导音色，不需要为每个音色重新训练模型。`speaker:0` 等标签区分角色，并不单独保证每次都使用同一个业务音色。稳定的业务音色应绑定经过验收的参考素材和音色版本。

模型在服务启动时加载并预热，一次启动服务于多个请求。代码中每个进程有自己的模型和生成线程，因此增加 `--workers` 会增加模型副本及显存消耗。

**四 目前实际开放的接口和能力**

| 接口 | 用途 | 对接注意事项 |
| --- | --- | --- |
| `POST /v1/tts` | 文本合成音频 | 支持 JSON 和 MessagePack；响应是音频字节，不是音频 URL |
| `GET /v1/tts/defaults` | 查询加载模型及采样默认值 | 可检查 `model_family` 是否为 `drama3` |
| `GET /v1/health` | 返回 `{"status":"ok"}` | 启动有预热，但此路由不主动检测生成线程或执行合成 |
| `/v1/references/add`、`list`、`update`、`delete` | 音色新增、列举、重命名、删除 | 管理接口应限制访问；目录必须持久化 |
| `/v1/vqgan/encode`、`decode` | 音频编码和解码 | 通常不需要给普通业务调用方开放 |
| `GET /ui` | 人工操作页面 | 源码需先构建；Dockerfile 包含前端构建步骤 |

已实现的主要能力包括普通 TTS、参考音频克隆、0～15 角色标签、文本内情绪提示、长文本分段、参考音色复用、非流式 WAV/PCM/MP3/Opus，以及只支持 WAV 的流式输出。各格式在目标镜像中的实际编码可用性仍需验收。

当前需要说明的能力边界：

- 本地 Drama 3 生成器完成一个文本段后才交付这一段音频；不能直接承诺逐音频帧输出的低首包延迟。`single_chunk=true` 会等整段生成，短文本也可能一次才收到全部音频。
- 模型资料介绍多轮修改与局部编辑，但当前 `ServeTTSRequest` 没有 `previous_takes`、编辑区域或会话历史字段，路由也没有相应接口。当前服务不能据此对业务承诺这些功能。分段间的内部历史不等于业务可调用的跨请求编辑会话。
- 服务启动时选择模型；`/v1/tts` 请求没有逐请求切换模型的字段。当前接口也不是 OpenAI 的 `/v1/audio/speech` 兼容协议。
- `normalize`、`latency` 字段存在，但在已检查的服务调用链中未见其实际使用；`repetition_penalty` 明确忽略。Drama 3 的分段路径使用自身规则，`chunk_length` 不直接控制其分段大小。
- 音色、采样率、格式、超时和流式接收方式应写入业务契约，不应让业务依赖未经验证的字段行为。

流式请求还需要定义途中失败的处理：响应头或 WAV 头发送后，后续推理错误通常无法再变成一个完整的普通 JSON 错误响应。客户端需要识别断流和不完整音频。首包统计应从首个可播放音频数据计算，不能把 WAV 文件头当成有效音频。

| 发布责任 | 谁部署、谁监控、谁接告警、谁决定回滚？ | 防止上线后故障无人处理 |

可以发给业务的开场文本：

> Drama 3 目前已有文本转语音、参考音色克隆、多角色和长文本分段的接口基础。为确定首版交付范围，请提供典型文本样本、目标音色及素材、峰值并发、首包与总耗时要求、音频格式和接入方式。我们会据此完成真实环境验证与压测，再共同确认测试地址、接口说明、验收标准和上线窗口。

不要在压测前承诺固定并发或毫秒级首包。RTF 表示合成耗时除以音频时长，例如花 5 秒生成 10 秒音频，RTF 为 0.5。RTF 小于 1 只说明对应测试条件下生成速度快于播放；仍需同时看等待时间和首个有效音频耗时。

**七 建议的首次交付范围和顺序**

首次联调可先约定：一个已验收固定音色、有限长度文本、明确的一种音频格式、一个受控调用方。对实时场景验证分段流式首包；对离线场景先完成整段音频质量和完整性验证。多轮编辑、跨请求会话、用户自助音色管理和大规模并发分别确认需求后再安排。

1. 业务提供代表性样本和指标，落实授权、负责人和验收人。
2. 平台分配固定 GPU 与运行环境，固定代码提交、权重版本和依赖。
3. 启动单实例，验证模型加载、预热、音色、格式和最短调用链。
4. 补齐请求限制、调度、错误处理、运行探针和日志；确定存储和鉴权方式。
5. 用真实业务样本验音质，再测不同长度和目标并发下的成功率、首包、总耗时、RTF 与峰值显存。
6. 业务在测试环境联调并签收；平台确认监控、故障处理和旧版本回退方式。
7. 小流量发布，达到约定指标后逐步放量。需要保留能承载业务的旧服务或备用实例，明确切回入口。

优先复用已经完成 16 并发测试的 vLLM-Omni 配置作为生产候选，补测业务参考音色、文本长度分布与稳定性，再确定容量。原生 API 可作为功能参考，若选择该路线则需要解决本表列出的调度问题。需要进一步优化时，再对比 SGLang-Omni 等受支持的推理后端。官方模型页提供了 SGLang-Omni 和 vLLM-Omni 的入口，官方性能表依赖其特定硬件和测试条件，不能代替目标环境的测量。[官方模型说明](https://huggingface.co/fishaudio/drama-3)

**八 首次启动和调用示例**

以下命令尚未执行。先由平台分配 GPU，将 `ASSIGNED_GPU` 设置为物理卡号，并通过约定的密钥系统设置 `FISH_API_KEY`。服务绑定本机，由平台网关或授权隧道接入；业务可访问的域名和网络策略另外配置。

```bash
cd /xhsq/zhangyue/code/tts/fish-speech

: "${ASSIGNED_GPU:?先设置平台分配的物理 GPU 编号}"
: "${FISH_API_KEY:?先设置测试服务密钥}"

CUDA_VISIBLE_DEVICES="$ASSIGNED_GPU" \
  /xhsq/zhangyue/conda_env/fishspeech/bin/python tools/api_server.py \
  --listen 127.0.0.1:8080 \
  --llama-checkpoint-path /xhsq/models/drama-3 \
  --decoder-checkpoint-path /xhsq/models/drama-3/codec.pth \
  --device cuda:0 \
  --workers 1 \
  --max-text-length 1000 \
  --api-key "$FISH_API_KEY"
```

这里的 `1000` 是示例限制，需要按业务样本调整。显式只暴露平台分配的一张卡后，进程内的 `cuda:0` 对应该物理卡。Drama 3 不使用 `--compile`。加载与预热可能需要数分钟；已有 Dockerfile 给启动健康检查预留 600 秒，但生产平台仍需自己配置探针。命令行密钥会成为进程参数，生产环境宜优先使用统一网关鉴权，或改造为受控的密钥注入方式。

```bash
curl --fail-with-body --max-time 180 \

```

**九 需要交付给业务和平台的材料**

| 材料 | 应包含什么 |
| --- | --- |
| 接口说明 | 测试/生产地址、鉴权、请求字段、音色 ID、音频格式与采样率、错误码、流式行为、限制和超时 |
